# 采集与数据质量

## 数据来源与请求预算

RSS 默认每 30 秒抓取一次，热榜每轮完成后等待 60 秒并叠加 0–15 秒抖动。热榜依次执行两轮双页采集和一轮四页采集；同轮页面间隔 2–3 秒，失败仍执行既有退避策略。每批最多接收 500 条已校验的列表记录，四页去重后超过 250 条仍可完整入库；采集页数、超时、stdout 大小限制及限流退避保持原有约束。网页轮询仅访问本地数据库。

作者信息优先使用公开列表中的帖子编号、作者名称和数字用户 ID。历史帖子可复用名称完全一致且仅关联一个已确认 ID 的身份记录；直接帖子证据优先，同名歧义不生成推测链接，大小写不同的名称不合并。排行榜仍按原有作者名称分组。详情补全遇到访问限制后，额外补全请求至少暂停 6 小时，避免连续历史查询反复延迟正常热榜采集。

仍未确认的作者按发帖数量排序，每次选择一个代表帖子读取原作者信息。补全复用热榜采集进程，最多每 2 分钟增加一个详情页请求（理论上限 30 次／小时，实际受热榜轮次、候选数量及退避影响）；同一名称尝试后 7 天内不再次选择。已在本轮列表中获取身份时不额外请求详情。详情页只解析公开页面配置中的原作者名称、ID 与帖子编号，校验通过后保存，不采集评论正文、用户私密资料或登录凭据。详情请求遇到 HTTP 403、429 或验证页时，共享源站采集至少退避 10 分钟，并遵守更长的 `Retry-After`。访问限制不会触发备用路径或立即重试。

## 帖子变更与订阅

同一论坛帖子以 `post_id` 识别。重复 RSS 条目只处理一次；标题、摘要、分类和作者与当前记录比较，有实际变化时仅更新当前内容，不保存旧版本。首次收录时间及原发布时间保持不变。无效或超过当前时间 5 分钟的 RSS 发布时间不替换为当前时间，该条目计入无效数据。

订阅仍使用既有精准规则，包括多关键词同时命中、显式正则、作者、分类及屏蔽词。内容同步不扩展 RSS 摘要的匹配范围，也不将详情页正文加入匹配。

| 原状态 | 内容更新后的行为 |
| --- | --- |
| 待匹配 | 保持待匹配 |
| 已匹配、待推送 | 保留队列状态，发送前仍由匹配流程复核 |
| 未命中 | 存在订阅且未删除命中时，重新进入精准匹配 |
| 已推送 | 保留成功状态、原规则关联与推送时间，不重新推送 |
| 已删除命中 | 保留移除标记，不重新展示或自动推送 |

推送入口同时检查数据库最新状态及同一进程中的在途发送，拦截已发送记录和并发重复调用。Telegram 未提供适用于该接口的客户端幂等键；上游已接收消息但响应丢失时，无法据此承诺跨网络故障的严格一次投递。

## 采集质量

RSS 配置页展示近 24 小时成功轮次、耗时、作者主页覆盖及最近 30 条采集记录。记录包含来源、时间、耗时、状态、返回与有效数量、新增与更新数量、无效条目、页数以及受控错误代码。部分 RSS 条目无效时记为“部分异常”，不丢弃本轮其余有效条目。

采集诊断最多保留 7 天且最多 10,000 条，实际保留区间同时受两项上限约束。诊断不保存代理 URL、原始异常文本、HTTP 响应正文、Cookie、令牌或密码。该接口与页面均要求有效会话。作者覆盖按已收录名称统计，存在同名 ID 歧义的名称不计为已关联。
